# 精简关键词提取与增量维护

本流程固化用户于2026-09-17核验通过的精简标签口径。适用于全库标签整理、新卡追加、卡文更新和标签维护；不是效果结构化、战斗模拟或自动阵容推荐流程。

## 输出与粒度

每个父记录一条，输出 JSON 数组，每条只含以下四个字段：

```json
[
  {"ID":"hero:5271","类型":"英雄","名称":"蒙恬","标签":["牺牲","召唤","逐鹿","二阶"]},
  {"ID":"hero:5061","类型":"英雄","名称":"云中君","标签":["闪现","开团","装备","升级","大河流域","三阶"]},
  {"ID":"hero:5171","类型":"英雄","名称":"大司命","标签":["牺牲","召唤","图腾","升级","回蓝","大河流域","四阶"]},
  {"ID":"hero:5251","类型":"英雄","名称":"鲁班大师","标签":["召唤","逐鹿","五阶"]},
  {"ID":"talent:637004","类型":"天赋","名称":"巨像","标签":["共战","召唤","等级门槛","三阶"]}
]
```

这些是经用户核验的粒度锚点，未来卡文改变时按新文重新提取，不为匹配示例而保留失效标签。不要往标签文件塞原文、伤害公式、次数、百分比、时间、条件树、证据段落或效果ID。不要先生成完整 `requires/produces/targets` 等机制树再压缩；直接阅读卡文概括关键词。

标签通常是2–4字的短词，少数正式名称可更长。每卡保留能区分核心用途的少量标签，不为凑数量添加“伤害、英雄、战斗”等泛词，也不设固定上限截断核心机制。核验基线平均3.62个、最多7个标签，只是当时数据统计，不是新卡的硬限制。

## 资料与标识

按 [资料定位](sources.md) 解析 `source_config.json` 的 `data_root`，默认相对本skill目录的 `data/`。直接读取当前 `documents/` 下五份源JSON，不依赖旧实验的 `labels_initial.json`、分片、绝对项目路径或固定行号。

| 类型 | 文件 | ID及名称字段 | ID前缀 |
|---|---|---|---|
| 英雄 | 王者万象棋_英雄牌.json | 卡牌ID、名称 | `hero:` |
| 效果牌 | 王者万象棋_效果牌.json | 卡牌ID、名称 | `effect:` |
| 天赋 | 王者万象棋_天赋牌.json | 卡牌ID、名称 | `talent:` |
| 装备 | 王者万象棋_装备牌.json | 卡牌ID、名称 | `equipment:` |
| 棋手 | 王者万象棋棋手详情.json | 棋手ID、棋手名称 | `player:` |

同名不同类型不合并，例如英雄镜与棋手镜。ID保留来源值并加类型前缀；同类型原始ID重复时，沿用已存在的稳定消歧ID，首次遇到则用原文定位后缀消歧并记录。缺ID时报告该项，不能用易变的名称冒充稳定ID。将其来源文件、JSON指针、名称、建议精简标签和待核验状态单列为待补清单，不写入正式四字段索引，也不生成空后缀ID。覆盖校验分别核对“有ID源记录＝正式索引”和“缺ID源记录＝待补清单”，汇报两者数量；取得ID后按当前原文重新核对并纳入增量核验。缺ID不妨碍按源定位读取原文参与构筑。

普通和觉醒是同一父卡，精简标签取核心主题的去重并集，不创建两张独立卡。只改数值的觉醒不加标签；若觉醒确实新增核心机制，加入该主题，但不表示普通状态也生效。预览/关联子卡用来理解父卡，不默认逐张另建记录，也不把全部子卡标签反向并入父卡。

## 提取规则

逐卡由 agent 阅读并判断主效果的关键词，脚本只负责ID、元数据、去重、合并和导出。不要对全文或旧效果字段进行关键词命中后全部收录。

1. **先取主效果主题。** 保留显著触发词、核心对象/资源和主要用途。英雄以主描述、正式关键词和觉醒新增主题为主；阅读技能用于理解，不逐项收录普通伤害、治疗、位移或每个战斗细节。蒙恬只取“牺牲、召唤”，不展开“同等级、士兵、分担伤害、持续20秒”。鲁班大师不展开预览傀儡的最高等级公式。
2. **按卡类判断主效果。** 效果牌、天赋、装备的描述本身就是主效果，所以可保留“护盾、回蓝、法伤、真伤、控制”等核心用途。棋手阅读技能、秘技、专属，概括主要玩法及资源；不把大量关联奖励逐项展开。比如巨像取“共战、召唤、等级门槛”，不继承预览蒙恬的“牺牲、逐鹿、二阶”。
3. **保留正式机制词，不偷换语义。** “开团、整备、牺牲、登场、退场、凯旋、败阵、合成、闪现、夺取、复生、转瞬”以主效果的实际关联为准。战斗开始不自动改写为开团，回合开始不自动改写为整备，普通死亡不自动改写为牺牲，一般复活不自动改写为复生。“召唤雷电”若只是伤害表现，不标成召唤单位；驱雷的核验标签为“法伤、普攻、特殊装备”。
4. **再补元数据。** 英雄、效果牌附源字段阵营（包括明确的无阵营/通用）；英雄、效果牌、天赋附自身品阶，统一中文数字如“二阶”。装备补“基础装备、普通装备、天赋装备、特殊装备”之一，不把优秀/稀有/传说品质改成品阶。棋手不编造阵营、品阶。
5. **区分自身属性与关联主题。** 无阵营字段的天赋不臆造阵营归属，但描述明确限制某阵营时可加该阵营作检索词。三分简称统一“三分之地”，大河简称统一“大河流域”。不能因目标是1–3阶，给一张五阶效果牌加“一阶、二阶、三阶”；也不凭被提及英雄的阵营推断天赋阵营。
6. **简短、去重、顺序一致。** 先机制/主题，后相关阵营与自身品阶或装备分类。无明确意义的空值不写成标签；不因每张英雄都有觉醒而统一加“觉醒”，不因父记录类型是英雄而统一加“英雄牌”。

## 用词归一

优先复用已有核验标签的用词。以下为常见映射，不是按字符串自动抽取的规则，也不是封闭词表：

| 原文含义 | 精简标签 |
|---|---|
| 阿科米亚核心 | 核心 |
| 英雄等级增加、永久升级 | 升级 |
| 临时等级 | 临时等级 |
| 法力值恢复 | 回蓝 |
| 法力值上限降低 | 减蓝 |
| 获得英雄牌/效果牌/战术牌/古币 | 英雄牌 / 效果牌 / 战术牌 / 古币 |
| 商店刷新、免费或临时刷新 | 刷新 |
| 物理/法术攻击力 | 物攻 / 法攻；两者一起时可用双攻 |
| 物理/法术伤害、真实伤害 | 物伤 / 法伤 / 真伤 |
| 物理/法术防御力 | 物防 / 法抗；两者一起时可用双抗 |
| 攻击速度、移动速度 | 攻速 / 移速 |
| 生命恢复、免疫控制 | 治疗 / 免控 |
| 同阵营、多阵营协同 | 同阵营 / 多阵营 |
| 英雄牌复制、等级复制 | 复制 / 等级复制，按对象区分 |
| 等级继承、转移、交换、转化 | 等级继承 / 等级转移 / 等级交换 / 等级转化 |

新增机制不能硬套旧词：确有独立核心用途时新增一个短标签，在变更摘要注明含义及为何已有词不足。同义词不要平行膨胀；不要为消除同义词而抹掉临时等级与永久成长、卡牌复制与等级复制等检索差别。

标签只表示主题相关，不区分提供、消耗、监听、筛选或排除。小乔带“登场”不证明小乔自身有主动登场效果；狂野帷幕带“牺牲”不证明它赋予牺牲。原文的否定和适用条件在具体联动研究时核查，不在精简标签里另建条件树。

## 全库整理与新卡更新流程

1. **确定当前输入及已有成果。** 使用本次指定的卡库/新增卡资料；查找用户提供或项目中现存的已核验精简JSON。首次全库整理时没有基线也可执行本流程。若用户已提供核验后导出文件，以该版本为标签基线，不用旧自动生成版本覆盖其修改。
2. **按类型+ID比较变更。** 新增卡创建记录；描述、关键词、觉醒、品阶、阵营或装备分类变更的卡重新阅读；未变卡保留已核验结果及顺序。改名且ID未变时更新名称，不当成新卡。若旧版原文/指纹缺失，不能仅凭标签相同声称卡文未变，应逐条回查本次范围。源中消失的ID单列移除清单，按本次全量同步或增量追加的任务范围处理，不能把增量输入误当全库删旧卡。
3. **直接填精简关键词。** 以本文件锚点检查粒度；主效果主题由阅读判断，元数据可机械补入。若缺主描述等关键来源，列入待补资料，不伪造标签；继续完成其他卡。
4. **校验后交付可核验结果。** 主数据为四字段JSON；附一份按类型列出的名称—标签表（Markdown或CSV）。交互HTML可选，不是复现流程的必要条件。增量任务突出新增/改动的前后差异及新增词；已核验旧卡不要求用户重新逐卡确认。新输出标为待核验，不因历史版本核验通过就宣称新卡也已通过。
5. **记录核验后的版本。** 用户确认或提供修改后文件时，将其作为后续基线；核验状态、源定位和指纹可独立记在版本/变更记录，不加进每张卡的四字段数据，也不要求原文随标签重复存储。除任务另有要求，不修改原始卡库、其他技能或运行BFS/评分。

源更新后总数动态计算，不能固定为529或固定六个分片；529只是已核验历史快照。每次直接从当前源读取，无须重跑历史的全效果标注实验。该流程不要求特定模型或子代理，遵循当前会话的模型与委派要求。

## 完成前检查

- 本次范围内源记录与输出ID集合一致，类型正确、同名卡未误合并；无重复ID、空标签或同卡重复标签。
- 字段只有 `ID`、`类型`、`名称`、`标签`，标签是短字符串数组；没有原文、数值公式和条件树。
- 品阶取卡牌自身，阵营不从预览卡或目标卡错误继承；装备和棋手不补造阶数。
- 用蒙恬、云中君、大司命、鲁班大师、巨像锚点检查粒度；在原文未变化的情况下保持用户已接受的结果。
- 检查新机制词、异常长标签及标签明显过多的记录，去掉只因全文命中产生的次要词；不机械要求每张卡相同数量。
- 源卡库保持只读；元数据检查只能证明覆盖与格式，不能代替语义阅读及用户核验。不要把“关键词齐全”宣称为全部机制已建模或标签连边已证明协同。
